## 1. 一次調査でわかった事実（実装判断の根拠）

### 1.1 素材（`eve_ui/`・実測）

| ファイル | 実寸 | モード | 用途 |
|---|---|---|---|
| `Live2D_background_inside.png` | 1264×843 | RGB | 奥背景（部屋） |
| `Live2D_background_foreground.png` | 2528×1686 | RGBA | 手前背景（机・キーボード。上部が透過） |
| `log_bvackground.png` | 2800×2000 | RGBA | チャットログ枠（角に装飾） |
| `text_background.png` | 2800×2000 | RGBA | 発話テキスト枠 |
| `Sample_layout.png` / `Sample_image.png` | 1400×1000 | — | レイアウト指定 |
| `nun model/` | Cubism 3系（`.moc3` + `.cdi3.json`） | — | Live2D 本体・テクスチャ 2048×2048 1枚 |

- **奥背景だけ解像度が半分**（1264×843 = 手前の 1/2）。手前と同じ倍率で使うと奥だけ甘くなる。
  等倍運用（論理 1400×1000）なら実害なし、HiDPI 150% では奥背景が拡大される。→ 差し替え or 許容を判断（§9 未決 U6）。
- `log_bvackground.png` は**綴り誤り**（`bvackground`）。採用時に `log_background.png` へ改名する。
- ログ枠/テキスト枠は角に装飾があるので、伸縮は **9スライス（CSS `border-image` 相当）**で行う。単純拡大は角が歪む。

### 1.2 Live2D モデルの実測（`nun model.cdi3.json` / `model3.json`）

パラメータ 27個・パーツ 10個。**実在するもの**:

```
ParamAngleX/Y/Z, ParamBodyAngleX/Y/Z, ParamBreath,
ParamEyeLOpen/ROpen, ParamEyeLSmile/RSmile, ParamEyeBallY,
ParamBrow(L/R)(Y/X/Angle/Form), ParamMouthForm, ParamMouthOpenY, ParamCheek,
ParamHairFront/Side/Back, Param
```

**ここから確定する制約（重要）**:

| 事実 | 帰結 |
|---|---|
| **`ParamA/I/U/E/O` が無い**（母音別の口形パラメータ非搭載） | **「あいうえお」の口形は再現できない**。口パクは `ParamMouthOpenY`（開閉量）＋ `ParamMouthForm`（口角）のみ |
| **`ParamEyeBallX` が無い**（眼球は縦のみ） | 視線の左右追従は不可。**首（`ParamAngleX`）で代替**する |
| `model3.json` の `Groups` は `EyeBlink: Ids[]` / `LipSync: Ids[]` が**両方とも空** | SDK の自動まばたき・自動リップシンクが**効かない**（P0 で実機確認: 自動まばたき ON でも6秒間 `ParamEyeLOpen`=1.0 のまま）。**手動でパラメータを毎フレーム書けば済む**ので model3.json の改変は不要 |
| `FileReferences` に **Motions が無い**（`.motion3.json` ファイル自体が存在しない） | **既製モーションはゼロ**。アイドル動作は**こちらで手続き的に生成**する（正弦揺れ＋呼吸＋物理） |
| `Expressions` 未参照（`damage.exp3.json` はフォルダにあるが model3.json から参照されていない） | 表情差分を使うなら model3.json に追記が要る |
| `Physics` はある（`nun model.physics3.json`） | 髪の揺れは首/体の動きから**自動で付く**（自前計算不要） |
| `nun model.vtube.json` が同梱 | 前作の VTube Studio 用設定。**今回は使わない**（VTS のホットキー定義等はそのままでは流用できない） |

### 1.3.1 P0 スパイクで実証済み（2026-08-13・`spike/live2d_test.py`・自己検証 2回連続 5/5 PASS）

**推測ではなく実機で確認した**（詳細は `spike/README.md`）:

| 項目 | 結果 |
|---|---|
| PySide6 + `QOpenGLWidget` + live2d-py で `nun model` が描画できる | **できる**（Cubism Core 05.01.0000） |
| 奥背景 → Live2D → 手前背景 の3層合成 | **成立する**。`QPainter` + `beginNativePainting()` で挟む。`live2d.clearBuffer()` は**呼ばない**（呼ぶと背景が消える） |
| `ParamMouthOpenY` を外部から毎フレーム駆動 | **できる**（`Update()` の**後**・`Draw()` の**前**に `SetParameterValue`） |
| 描画レート / HiDPI | **61fps** / devicePixelRatio 1.50 が効いて 1350×900px で描かれている |
| SDK の自動まばたき | **効かない**（6秒間 `ParamEyeLOpen`=1.0 のまま）＝1.2 の読みが実機で裏付けられた |

**リップシンクは RMS（音量包絡）では不十分だと実測で判明**し、方式を変更した:

| 方式 | 開口率 | 閉じ/秒 | 実モーラ速度 |
|---|---|---|---|
| RMS（窓・レンジ・release を54通り掃引した最良） | 87% | **2.4** | 5.0 /秒 |
| **モーラ長（`audio_query` の consonant_length / vowel_length）＝採用** | 72〜78% | **5.1〜5.2** | 5.0 /秒 |

日本語 TTS は母音が連続して有声のまま繋がるため、**モーラの切れ目が振幅の谷にならない**
（＝どうパラメータを振っても口が開きっぱなしに見える）。`audio_query` にモーラ長が入っているので、
音声解析をやめてそちらから組み立てる。採用値: 子音の開き 0.08 / attack 20ms / release 40ms。

### 1.4 既存コード側の制約（一次ソース確認済み）

| 事実 | 出典 | UI への影響 |
|---|---|---|
| `Config` は import 時に `.env` を1回読むだけ。`_load_dotenv` は `os.environ.setdefault`（既存の環境変数が勝つ） | `eve/config.py:13-31` | **設定の反映は「別プロセスで起動し直す」しかない**。同一プロセスで `.env` を読み直しても効かない ＝ R8 と構造が一致している |

| `asyncio.create_subprocess_*` も `signal.*` も**使っていない**（子プロセスは素の `subprocess.Popen`） | `workspace/capabilities.py:95` ほか grep 全件 | **asyncio ループをメインスレッド以外で回して安全**（＝Qt をメインに置ける） |
| `ModelRegistry.set_override(role, model_id)` が既にある（「UI からのモデル差し替え用」） | `model_registry.py:96` | モデルだけは即時切替も技術的には可能（ただし R8 に従い既定は再起動） |

## 2. 画面構成

論理座標 **1400×1000**（`Sample_layout.png` と同一）で組み、ウィンドウは**アスペクト比固定**でスケールする。

```
┌──────────────────────────────────────────────┬───────────────┐
│ [停止] [自律発話] [画面認識] [タスク] [設定]  │               │  ← メニュータブ y:0-100
├──────────────────────────────────────────────┤   チャット    │
│                                              │   ログ        │
│   ┌── 奥背景（部屋）───────────────────┐   │               │
│   │        Live2D（イブ）                │   │  log_back-    │  x:1000-1400
│   │   ── 手前背景（机・キーボード）──    │   │  ground.png   │  y:0-730
│   └──────────────────────────────────────┘   │   の枠内      │
│                          x:0-1000 y:100-730  │               │
├──────────────────────────────────────────────┴───────────────┤
│  text_background.png の枠内 ＝ イブの発話テキスト（今喋っている文）  │  y:730-1000
└──────────────────────────────────────────────────────────────┘
```

- メニュータブは**タブ**として機能し、「設定」を押すと右のログ領域＋Live2D 領域が**設定ページに差し替わる**（R9）。
  Live2D を隠すか残すかは §9 未決 U2。
- ON/OFF ボタンは 4状態を持つ（§4.1）: **ON=不透明 / OFF=半透明グレー / 切替中=点滅＋「切替中…」**。
- 発話テキストは**今喋っている1文**を大きく出す（ログとは役割が違う）。喋り終わったらフェードで薄くする。

## 3. アーキテクチャ決定

### 3.1 GUI ツールキット: **PySide6 を推奨**

| 案 | Live2D | 装飾（枠画像・角丸・半透明） | 総合 |
|---|---|---|---|
| **A. PySide6 + `QOpenGLWidget` + live2d-py**（推奨） | live2d-py が明示サポート | QSS の `border-image` で9スライスがそのまま書ける。HiDPI/フレームレス/最前面が標準 | ◎ 単一言語・実績経路 |
| B. Tkinter + `pyopengltk` + live2d-py | 動く見込みだが `pyopengltk` 0.0.4 に全依存 | Canvas 手描きになり、ログのスクロール＋折返し＋枠画像がかなり苦しい | △ 原契約は Tkinter だが装飾要件と噛み合わない |
| C. pywebview(WebView2) + `pixi-live2d-display` | Web 版 Live2D は最も枯れている | HTML/CSS＝この意匠に最強 | ○ ただし Python↔JS の橋が増え、最前面/キャプチャ除外など OS 制御が遠い |

**推奨理由**: R6（3層背景）・R2（アコーディオン等の作り込み）・R4 を1つの言語で満たせるのは A のみ。
既存 `viewer.py` の Tk は当面そのまま残してよい（§4.5 で吸収する）。
**依存は 77.5MB 増える**（LGPL・pip の動的リンク利用なら MIT アプリ側に伝播しない）。

> **B/C を採るなら §7 の P0 で判定する。P0 の目的はまさにこの選定を実測で決めること。**

### 3.2 プロセス／スレッドモデル: **Qt=メインスレッド / asyncio=ワーカースレッド**

`PIPELINE_DESIGN §9.1` が既に「UI は別途メインスレッド。widget 更新は `root.after(0,fn)`、UI→loop は
`run_coroutine_threadsafe`」と定めている。Qt 版ではこうなる:

```
[メインスレッド: Qt]                          [ワーカースレッド: asyncio loop]
  QMainWindow / QOpenGLWidget(60fps)            VoiceLoop 一式（既存コードは無改造が原則）
  UiState（表示用の値のコピーだけを持つ）
        ▲  Qt signal（queued connection）           UiEventBus.emit(dict)   ← loop 上から
        │  ※ dict/dataclass の**値のコピー**のみ
        └───────────────────────────────────────────────
        │  loop.call_soon_threadsafe(control.request, ...)  → ControlPlane（loop 所有）
        ▼
```

**不変条件（§9.3 の UI 版・破ったらビルド失敗にする）**:
1. **UI スレッドは loop 所有 state（StimulusQueue / AudioPlayQueue / PredictionState / caches / TaskStore）を読まない。**
   読むのは「loop が作って投げたスナップショット」だけ。
2. **UI→loop は `call_soon_threadsafe` 一択**（結果が要る操作は作らない＝§9.3 手段2 を常用しない）。
3. UI が落ちても loop は生き、loop が落ちたら UI は「停止」を表示して終了できる。
4. `tools/voice_chat.py`（ヘッドレス）は**今後も一級の実行経路として残す**。E2E ハーネス
   （`tools/search_e2e_test.py`）は VoiceLoop を直接叩くので、**UI を通さずに全テストが回り続ける**。

> qasync（Qt イベントループ上で asyncio を回して1スレッドにする）も検討したが**不採用**。
> VAD 推論が現状ループ上同期（`PIPELINE_DESIGN §9.2`）なので、60fps 描画と同居させると
> マイク入力にジッタを入れうる。分離しておけば描画は応答予算（≤3s 理想 / ≤5s 許容）に触れない。

### 3.3 loop → UI に流すイベント（追加する最小フック）

| イベント | 発生源 | 既存フックの有無 |
|---|---|---|
| `user_text`（STT 確定） | `response/input_source.py:92` | ログ出力箇所に1行足すだけ |
| `eve_sentence_start(text)` | `AudioPlayQueue.play_worker` | **新設**（`_Item.text` は既にある。再生開始で呼ぶ） |
| `eve_sentence_played(text)` | 同上 `on_played` | 既存（`orchestrator.py:411`） |
| `state`（listening / thinking / speaking / busy） | `speech_state` + `runner.is_busy()` | 既存の値を周期（4Hz）で snapshot |
| `mic_level`（VAD 振幅） | `audio_input` | 新設（表示専用・値のみ） |
| `task`（1件制なので常に0〜1件＋経過秒＋手数） | `TaskStore` | 既存 `active_tasks_for_context` を流用 |
| `vision`（直近実況テキスト・任意でサムネ） | `VisionState.latest_vision` | 既存 |

| `feature_state`（各機能の ON/OFF/切替中） | ControlPlane | 新設 |

**すべて「値のコピーを投げる」だけ**。UI 側に参照を渡さない。

## 4. 機能仕様

### 4.1 メニュー（R1・R7・R9）

#### ON/OFF の安全切替 — 状態機械

```
OFF ──要求ON──▶ STARTING ──完了──▶ ON ──要求OFF──▶ STOPPING ──drain完了──▶ OFF
                    ▲                                   │
                    └──────── 要求は latest-wins ────────┘
```

- 押した瞬間に反映しない。UI は即座に **STARTING/STOPPING（切替中）**表示に変わり、
  **loop 側が「安全地点」に到達してから**実際に切り替え、完了イベントで UI が確定表示になる。
- 切替中の連打は**最新の意図だけ**を保持する（サイドカー契約 §9.4 の latest-wins と同じ流儀）。
- ControlPlane は loop 所有の単一オブジェクト。**切替は必ず loop 上で実行**する。

#### 機能ごとの「安全地点」

| 機能 | OFF にしてよい条件 | 実装 | 再 ON の要件 |
|---|---|---|---|
| **停止/再開** | 進行中の応答が**最後まで喋り終わる**（or ユーザが明示中断）＋マイクを解放 | `input.stop()` → 新規刺激の生成を止める | `input.start()`（`AudioInput` を作り直す・既に対応済） |
| **自律発話** | 発話判定が**走っていない**（`decider._idle`）／判定中なら完了を待つ | `silence_monitor.stop()` → `speech_decider.stop()`（drain 実装済） | **`_stopping` のリセットが必要**（現状 restart 不可） |
| **画面認識** | 進行中の VLM 呼び出しが**完了**するまで | `capture_thread.stop()`（join は `to_thread`）→ `vlm_worker.stop()` → `VisionState` をクリア | **`CaptureThread` を再生成**＋`_stopping` リセット |
| **タスク** | **アクティブ0件かつ未配達の完了報告0件**（＝1件制の枠が空く）まで待つ | 待機中は既存の1件制ゲートで新規 `delegate_task` を断る → `registry.unregister()` で `delegate_task`/`cancel_task`/`search_web`/作業フォルダ系を**束で外す** | 同じ束を `voice_loop.__init__` と**同一順序**で再登録 |

**タスク OFF は最長 `TASK_AGENT_TIMEOUT_SEC`=600秒待つことがある。**
→ UI は「今のタスク（目標・経過秒）」と **［今すぐ取り消して OFF にする］** を並べて出す。放置で固まったように見せない。

**副次的な良い性質**: タスクを外すと `outward_actions()` が自動で縮むので、
応答LLM の「実際に実行できる手段」ブロックが**勝手に整合する**（D3 の設計＝手書きしない、が効く）。

#### 終了（R3）

ウィンドウの × で `VoiceLoop.stop()` を呼び、**drain 完了まで「終了中…」を表示してから閉じる**（即閉じない）。
`eve/cleanup.py` の `sweep(phase="shutdown")` は既に stop の内側にある。
UI プロセスが強制終了された場合も、次回起動時の `sweep(phase="startup")` が回収する（既存の両端方式がそのまま効く）。

### 4.2 設定タブ（R2・R8）

**原則: 保存 → `.env` へ書き出し → ［保存して再起動］で新プロセスを起動して自分は終了。**
（`Config` が import 時1回読みなので、同一プロセスでの再読込は**構造的に効かない**。R8 と一致。）

`.env` は gitignore なので、変更は必ず `.env.example` にも項目を足す（**D6 の再発防止・CLAUDE.md の規律**）。

#### 「自発発話頻度」の抽象化 — 何にマップするか（重要）

**やってはいけないこと**: surprise の数値ゲートを作ること。
CLAUDE.md の中核原理「surprise は数値で発話を絶対決定しない（Fix2 裁定・生存中）」に真っ向から反する。
J-2 ③で撤廃した「沈黙バイアス」を別名で復活させるのも不可。

**やること**: **判定のカデンス**（＝発話判定LLM を何秒沈黙で回すか）を動かす。

| 表示 | `SILENCE_THRESHOLD_SEC` | 補足 |
|---|---|---|
| ひかえめ | 10s | 判定回数が減る＝API コストも減る |
| ふつう（既定） | 5s | 現行値・企画書準拠 |
| おしゃべり | 3s | 判定回数が増える＝**API コストが増える**ことを UI に明記 |

**効果の判定は「件数」でなく「speak率 = 発話数 ÷ 判定回数」で見る**（CLAUDE.md 落とし穴 #7）。
既知のベースライン: 通常 0.092 / 動画視聴中 0.17（`HANDOFF.md`）。

### 4.3 チャットログ / 発話テキスト

- ログの1行は **種別で色分け**する: `ユーザ` / `イブ` / **`自発発話`** / **`タスク報告`** / `画面認識` / `システム`。
  この6つは**パイプライン上まったく別の経路**なので、見分けが付くと不具合の切り分けが劇的に楽になる

- 発話テキスト欄は**今喋っている1文**。`eve_sentence_start` で差し替え、barge-in で即座に消える

### 4.4 Live2D（R4・R6）

#### 描画構成（1つの `QOpenGLWidget` の中で完結させる）

```
奥背景（テクスチャ付き四角形）→ Live2D モデル → 手前背景（RGBA 四角形）
```

Qt のウィジェット重ね合わせ（QLabel を透過 GL の上下に置く）にしない。**合成順を GL 内で持つ方が確実**で、
将来「机の上に置いた小物」など層を足すのも同じ仕組みで済む。
→ ただし live2d-py がクリアや GL ステートをどう触るかは**未確認**。P0 の検証項目 #2。

#### 動かし方（既製モーションが無いので手続き的に作る）

| 要素 | 実装 | 根拠 |
|---|---|---|
| **口パク** | VOICEVOX `audio_query` の `accent_phrases[].moras[].vowel/vowel_length` を **TTS の戻り値に同梱**し、再生開始時刻を起点に `ParamMouthOpenY` を駆動 | **P0 で実証・採用確定**。母音別の開き量（あ1.00/え0.72/お0.62/い0.42/う0.34/ん0.18）＋ 子音0.08 ＋ attack 20ms / release 40ms。query は**既に取得して捨てている**（`tts.py:47`）。`speedScale` で割るのを忘れない |
| （代替）音量追従 | 再生 PCM の RMS 包絡 → `ParamMouthOpenY` | **主方式には使えないと実測で判明**（1.3.1）。日本語 TTS は振幅に谷が出ず口が開きっぱなしになる。VOICEVOX 以外の音源用のフォールバックとしてのみ残す |
| **まばたき** | 3〜6秒のランダム間隔で `ParamEyeLOpen/ROpen` を 閉80ms→開140ms | `model3.json` の EyeBlink グループが空なので**自動まばたきは効かない**（1.2・**P0 で実機確認済**） |
| **呼吸・アイドル** | `ParamBreath` = 正弦（周期 ~3.5s）、`ParamBodyAngleX/Y` に微小ノイズ | 髪は physics3 が自動で追従する |
| **視線** | マウス座標 → `ParamAngleX/Y`（首）＋ `ParamEyeBallY`（縦のみ） | `ParamEyeBallX` が無い（1.2） |
| **surprise 連動** | `PredictionState.surprise`（0-1）→ 揺れ幅・首の振り・`ParamBrow*` の振幅倍率 | **原契約 §6「予測誤差が大きいほど動きを激しく」の実装**。<br>**表示専用**であり、UI は surprise を**読むだけ**（書かない・挙動を変えない）＝中核原理に触れない |
| 状態表現 | 考え中＝わずかに視線を外す / 聞いている＝正面 / タスク実行中＝時々うなずく | 状態は §3.3 の `state` イベントから |

#### VRM 案について

- VRM は本来 3D（VRM 1.0 / glTF 拡張）で、Python 実装は Live2D ほど整っていない。
  **「難易度が低い」とは言えない**（描画・スプリングボーン・表情の BlendShape をほぼ自作になる）。
- 加えて**素材が既に Live2D で揃っている**（`nun model` + 部屋の2層背景は「PC の前に座っている」構図に作られている）。
  3D に替えると背景2層の意味がなくなる。
- **→ Live2D を推す。** VRM に行くのは P0 で Live2D が実測不能と判明した場合のみ。

### 4.5 AI の画面表示をウィンドウ内に（R5）

現状: `show_on_screen` → 別プロセスの Tk ビューア（`workspace/viewer.py`）が自由な位置に開く。最大5窓。

| 案 | 内容 | 得るもの | 失うもの |
|---|---|---|---|
| **A（推奨）** | UI プロセス内に**表示ペイン（第2ウィンドウ or ドック）**を持ち、`show_on_screen` は「パスを UI に渡す」だけにする。複数はタブ | 位置が暴れない／閉じ忘れゼロ（**E2 の孤児窓が構造的に消える**）／意匠が統一／`close_window` が確実 | **クラッシュ隔離を失う**（壊れた画像のデコード落ちが UI ごと落とす）。`viewer.py` の設計理由の1つ |
| B | 別プロセスのまま Win32 `SetParent` で UI に埋め込む | 隔離を保ったまま「窓の中」 | フォーカス・DPI・Z順が壊れやすい。**非推奨** |
| C | 別プロセスのまま、**位置とサイズだけ**を UI の指定矩形に制約 | 実装が最小・隔離を保つ | 見た目は「重なった別窓」のまま＝R5 の意図に届かない |

**推奨 A ＋ 逃げ道**: `WS_VIEWER_MODE=window`（既定・UI 内）/ `external`（現行の別プロセス）を設定で切替。
A を採る場合も **`viewer.py` の安全規律をそのまま移植する**こと:
- 拡張子を信じずマジックバイトで判定（`sniff`）
- **`os.startfile` を使わない**（作業フォルダに `.hta`/`.lnk` を書けば任意アプリ起動に化ける）
- 作業フォルダ外は表示しない（呼び出し側と表示側の**二重検証**・TOCTOU 対策）
- `MAX_IMAGE_PIXELS` / サイズ上限（decompression bomb）
- デコードは `try` で囲み、失敗しても「表示できませんでした」に落とす（**UI を巻き込まない**）

### 4.6 画面認識との相互作用（**設計上いちばん危ないところ**）

UI がイブのログと表示内容を画面に出す ＝ **VLM が自分の出力を「ユーザの画面」として実況する**（D4 / E11）。
現行の緩和は「この窓はあなた自身が開いたもの」を VLM に注入する方式（第2弾で実装済）だが、
**UI が常時全画面に居座ると比重が変わる**。構造解を用意する:

#### 実測で3方式を比較した（2026-08-13・1680×1050・DPI 150%）

目印色のウィンドウを出し、`mss`（＝本番の `ScreenCapture` と同じ経路）で撮って確かめた:

| 方式 | 実装 | 矩形内に窓が写った割合 | OBS |
|---|---|---|---|
| 対照（何もしない） | — | **92.1%**（＝ふつうに写る） | 映る |
| **① DisplayAffinity 除外** | `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` | **0.0%** | **映らない** |
| **② 矩形マスク** | `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` で枠を取り、**自分が撮ったバッファ上で**塗り潰す | **0.0%** | **映る** |

#### 追加の実測（2026-08-13・ユーザ指摘「黒塗りが AI に届いてもヤバい」を受けて）

**黒塗りは「画面が真っ黒」という新しい実況材料を作る**（＝イブが黒い矩形に反応する）ため、
「窓が消えているか」だけでなく**跡地に何が写るか**を測り直した。
大きいシアン窓（ユーザのアプリ役）の上に小さいマゼンタ窓（イブの UI 役）を重ねて計測:

| 方式 | 跡地の中身 | 黒画素 | AI から見た状態 |
|---|---|---|---|
| 対照（除外なし） | マゼンタ 92.2% | 0.0% | イブの窓がそのまま見える ❌ |
| **① DisplayAffinity 除外** | **シアン 98.6%**（＝**背後の内容が合成される**） | **0.8%** | **窓が最初から無かったのと同じ** ✅ |
| ② 矩形マスク（黒塗り） | 黒 100% | 100% | 窓は消えるが**黒い矩形に反応する** ❌ |

**→ `WDA_EXCLUDEFROMCAPTURE` は黒い穴を空けない。DWM が背後を合成する。**
この一点で ① と ② の優劣は逆転する（②は AI 要件を満たさない）。

#### 結論と、OBS との両立

| 要件 | ① DisplayAffinity | ② 黒塗りマスク | ③ crop（端に寄せて切り落とす） |
|---|---|---|---|
| AI に窓が届かない | ✅ | ✅ | ✅ |
| AI に黒い矩形が届かない | ✅ | ❌ | ✅ |
| OBS に映る | ❌ | ✅ | ✅ |
| 制約 | — | — | **UI が画面の端に接している時だけ成立** |

#### 裁定（ユーザ 2026-08-13）: **① DisplayAffinity を既定とし、設定で ON/OFF できるようにする**

根拠（ユーザ）: 「**今後の配信時は基本的に画面認識を行わない想定**」。
配信と画面認識が同時に走らないなら、①の唯一の欠点（OBS からも消える）は**実運用で衝突しない**。
衝突する時だけ設定を OFF にすればよく、③ crop の「端に寄せる」運用制約を常時背負う必要がない。

- 設定項目 **`UI_HIDE_FROM_CAPTURE`**（既定 ON）を新設。§4.2 の設定タブに出す。
- **この設定だけは即時反映してよい**（`SetWindowDisplayAffinity` は実行中の切替が効くことを実測済:
  除外 0.0% → 解除 92.1%）。`.env` 経由の再起動が要る他の設定とは性質が違う（Config を読まない）。
- ② 黒塗り・③ crop は**実装しない**（必要になったら本節の実測が残っているので後から足せる）。
- OFF にした時（＝配信時）は、イブが自分の窓を見る状態に戻る。既存の E11 対策
  （「この窓はあなた自身が開いたもの」を VLM に注入）はそのまま残っているので裸にはならない。

消しているのは**イブが Gemini に送る画像と、変化検出に使う画像だけ**で、対象は
**イブ自身の2窓のみ**（メイン UI と表示ペイン）＝ユーザのアプリには影響しない。

実装は `eve/vlm/capture.py` の `capture_one()` / `grab_png()` に「マスク矩形を返す関数」を1つ
注入するだけで済む（pHash・OCR・送信 JPEG のすべてが同じバッファ由来なので**1箇所で全部に効く**）。

補足の実測: **窓の中身を大きく書き換えた前後の pHash 距離はマスク無しで 4**（閾値12 未満）。
つまりイブのログが流れても pHash は起きない一方、**マスクすると距離 0** になる。
pHash が鈍いことは既知（HANDOFF の文字ゲート節）なので、マスクが本当に効くのは
**(a) 文字ゲート（OCR）の誤発火**と **(b) Gemini に送る画像に自分のログが写り込むこと**の2つ。
特に (b) は E11 自己観察ループそのもので、UI が常時画面に出る以上いちばん効く対策になる。

**①も実装しておく価値はある**: 実測で**実行中に ON/OFF を切り替えて元に戻せた**（0.0% → 92.1%）。
「配信中はマスクのみ / 配信していない時は OS レベルでも隠す」といった使い分けが後から選べる。

既知の限界（実装時に決める）:
- 他のウィンドウがイブの窓の**上に重なっている**と、その部分もマスクされてユーザの内容が消える。
  厳密にやるなら z 順で上位の窓の矩形を引き算する（約20行）。まずは単純な矩形で始めてよい。
- マスクが画面の大半を占めると `VLM_BLANK_STD_THRESHOLD=6.0`（黒画面＝取得不可の検出）に
  引っかかりうる。**分散はマスク外の領域で計算する**こと。
- 窓を動かすとマスク矩形が動くので pHash が変化を拾う（＝実際に画面が変わっているので正しい挙動）。

②を入れても、E11 対策の「この窓はあなた自身が開いたもの」注入と E2 の窓自動クローズは
**実測で不要と確認できるまで外さない**（HANDOFF の E11/E2 は「部分的」評価のまま）。

（参考）`VLM_MONITOR` を別モニタに向ける既存機能でも回避できるが、マルチモニタ環境限定。

## 6. 技術的にできないこと・制約（正直な報告）

| 1 | **母音別の口形（あ/い/う/え/お の口）** | モデルに `ParamA/I/U/E/O` が無い（実測）。口は**開閉量＋口角**のみ |

| 5 | **ウェブカメラの顔トラッキング**（VTube Studio 相当） | 今回のスコープ外。必要なら別企画 |

## 7. 実装順序（安全に積む）

原則: **どの段階でも `tools/voice_chat.py`（ヘッドレス）と E2E ハーネスが壊れない**。
UI は VoiceLoop の**外側の殻**として積み、本体の改造は「イベントを外に出す小さなフック」に限る。

| 段 | 内容 | 完了条件（これが出るまで次に進まない） |
|---|---|---|
| **P0** | **技術検証スパイク（`spike/live2d_test.py`・捨てるコード）** | **完了（2026-08-13）**。①モデル描画 ②3層合成 ③`ParamMouthOpenY` 外部駆動 ④61fps・HiDPI ⑤キャプチャ除外 — **すべて Yes**（自己検証 2回連続 5/5 PASS）。§3.1 の PySide6 案で確定。リップシンクは RMS 不可・モーラ長方式に決定（§1.3.1）。<br>**残: フレームレス／最前面／アスペクト固定は未検証**（P1 で確認する。標準機能なのでリスクは低い） |
| **P1** | **観測専用 UI（ボタンは全部無効）**<br>Qt メイン + asyncio ワーカースレッド、§3.3 のイベント配送、ログ・発話テキスト・状態表示 | UI から**何も操作できない**まま、実起動と同じ会話ができる。ヘッドレス経路が無傷。UI を落としても loop が生きる |
| **P2** | **前提工事**（本体側の小改修）<br>`_stopping` のリセット、`CapabilityRegistry.unregister`、`AudioPlayQueue` の再生開始フック、`VV_INTONATION` | Tier-1 が **495件 PASS を維持**（2回連続）。追加分のテストも PASS |
| **P3** | **停止/再開 と ミュート**（いちばん影響が小さい制御で状態機械を作る） | 発話の途中で停止 → 喋り終わってから停止する／再開でマイクが戻る、を2回連続 |
| **P4** | **自律発話 ON/OFF・画面認識 ON/OFF** | OFF→ON→OFF を各3回。判定中/VLM 呼び出し中に押しても壊れない。OFF 中に自発発話・実況が**1件も出ない** |
| **P5** | **タスク ON/OFF**（最難関） | 実行中に OFF を押す → 報告を配達し終えてから OFF。同時アクティブのピーク ≤1 を維持。再 ON で `delegate_task` が復活し `outward_actions()` も戻る |
| **P6** | **設定タブ**（`.env` 書き出し＋再起動＋起動診断パネル＋`.env.example` 同期） | 全項目を変更→再起動→**起動診断パネルに反映が出る**。`.env` のコメントとキーが壊れない |
| **P7** | **表示範囲のウィンドウ内化**（§4.5 A・`external` へ戻せる状態で） | `show_on_screen`×5 → 全部ウィンドウ内タブ／異常終了後の孤児窓ゼロ／壊れたファイルで UI が落ちない |
| **P8** | **Live2D 本実装**: 口パク → まばたき → 呼吸/揺れ → 視線 → surprise 連動（**各段で止められる順**） | 60fps（最低30fps）を維持したまま、**応答レイテンシが P1 比で悪化しない**（日常会話の中央値で比較） |

**ブランチ**: 段ごとに切る（`feat/ui-p0-spike` → `feat/ui-p1-readonly` …）。CLAUDE.md「機能ごとに branch」。

## 8. テスト方針

| 層 | 何を | どこで |
|---|---|---|
| **Tier-1（決定論・API不要）** | **ControlPlane の状態機械**（OFF→STARTING→ON→STOPPING、latest-wins、切替中の連打、安全条件の待機）を **UI 非依存の純ロジック**として。`unregister` 後に `outward_actions()` が縮むこと | `tests/test_ui_control.py`（新規）。GUI は持ち込まない |
| Tier-1 | イベント→スナップショット変換（値のコピーであること・loop 所有オブジェクトの参照が漏れないこと） | 同上 |
| **回帰** | 既存 **495件 PASS を維持**（P2 以降は毎回） | 既存 `tests/` |
| **実機** | 既存 E2E は**ヘッドレスのまま**維持（UI を通さない）。UI 経路は P10 で代表シナリオのみ | `tools/search_e2e_test.py` は無改造 |
| **UI 手動チェックリスト** | 起動診断パネルの全項目・切替中表示・画面外復帰・異常終了後の掃除 | `docs/HANDOFF.md` に手順を追記 |

**やらないこと**: GUI の自動操作テスト（pytest-qt 等）を今回導入する。費用対効果が合わない。
状態機械をロジックとして切り出し**そこだけを決定論テストで固める**方が、同じ欠陥クラスを安く捕まえられる
（E13 の反省＝テストが欠陥クラスを守れていない、を繰り返さない）。
