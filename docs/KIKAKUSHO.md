## 0. 全体方針（リアルタイム性）

- OpenAI Realtime API / Gemini Live のように、音声認識・LLM を**数百ms単位の塊でストリーミング**処理。
- 入力 50〜300ms ごと、出力は token streaming で発話。**早くできた音声はキューに溜め順番に流す**。
- 応答LLM はリアルタイム性、速度と精度を両立。構造上入力が大きくなるため**ある程度精度あるモデル**を使用。
- リアルタイム維持のため可能な所は非同期・ストリーミングで高速化。
- 無言/何も入っていない時はそのまま最速で刺激を入れる。応答中・入力中はキューに溜め完了後に入力。
  - Call-Function 刺激が2つ以上 → 順番にキュー消化。
  - 画面認識・フィードバックは2つ以上 → **統合**してキュー消化。
- **フィードバックLLM は遅延前提**（タイムスタンプで遅延認識・遅くてよい処理＝人間の内分泌系のイメージ）。
- **応答LLM は即時性**（人間の神経系のイメージ）。

## 1. 応答LLM

- 入力: ユーザー発話 / システムプロンプト / 直近会話5ターン / RAG2件 / 直近フィードバック1件 /
  画面認識情報（Claude Sonnet 由来） / 発話判定 / Call-Function。
- 出力: token streaming で発話。

## 2. フィードバックLLM（FEP・非同期）

- 入力: システムプロンプト / 前回のフィードバックLLMの応答 / 前回フィードバックに含まれず応答LLMに
  入れていたもの / 応答LLMが出したもの。
- 出力: 感情 / 直近会話の要約 / ユーザーの感情推測 / 次の会話の簡易予測 /
  **前回予測との差を数値で分析（0〜100）**。
- **無言時**: 思い出したRAGや画面情報から、応答LLMに**話題を提案**する。

## 3. 発話判定LLM

- 入力: 「…」 / 直近の会話 / RAG / 画面情報。**ユーザー5秒無言で「…」を送る**。
- 黙るべき → 「…」を返す。話すべき → 応答。
- 基準: 直近会話・RAG・画面情報から文脈的に、話す内容があるか・現時点で疑問はないか等を**総合判断**。
- **ランダムなRAG2件**を材料に。
- 話す → True + なぜ話すかの理由 + そのまま入力された内容を応答LLMに入れて話させる。
- 黙る → False + なぜ話さない理由を出力。**応答LLMには入れず発話判定ログへ**（出力させないと楽なFalseに偏る）。
- **発話判定ログ**: True/False とも記録・10件ロケット鉛筆（処理には関与しない）。

## 4. 記憶

- **RAG**: 1チャンク = フィードバック1応答。**300件ロケット鉛筆**で最新に更新。なるべく意味が近いものを
  持ってくる。できれば連想できるものでもよい。
- **直近ターンログ**: **100件ロケット鉛筆**で最新に保つ。「…」連続は「…×X」と圧縮して記録。
- **タイムスタンプ**: 各AI/ユーザー発話に付けてログ・RAGへ保存。

## 5. 画面認識

- Gemini Flash 2.5 の画像認識は 0.3〜1秒。画面をスクショ→説明させる。
- 入力〜出力を高速で**3回**回し、少し賢い **Claude Sonnet で3回分を統合**して画面の動きを抽出
  （Flash=大まかな動き、Sonnet=画面文字など細かい所）。
- 画面変化が1%等の微細では無駄 → スクショ後に**画面変化量を計測、30%以上で LLM に入れる**。
- 3回とも変化なし → Sonnet を飛ばしルールベースで「画面変化なし」。1回目変化/2回目なし/3回目変化でも
  タイムスタンプを振れば Sonnet が解釈できる。
- **アクティブウィンドウ**（何を開いたか・どうページが変わったか）や**入力操作**（マウス/キーボード）を
  検知して画面認識を取りに行く / Sonnet 要約に入れるのもあり。

## 6. Live2D

- フィードバックの前回予測との差が大きいほど動きを激しく。喋っている時も動きを激しく。

## 11. YouTube 配信モード

- 応答LLMをより高度なモデルに（Opus 4.8 等。リアルタイム性が要らなくなるため）。YouTube用システムプロンプトに変更。
- **タスクのみ** Call-Function 使える。YouTube APIキーからユーザー名・チャットを取得、上から1つずつ。
- 情報が多く混戦しうるためパイプラインを念入りに確認。

## 12. UI

- 各LLM（応答/フィードバック/画面認識）を変更。LLM の温度やシステムプロンプト等を変更。ログ表示。
  モード切替。画面認識 on/off。スタート/ストップ。その他 config。
- **スタート中は設定をいじれない。ストップ中のみいじれる。** 全て設定完了し安全に動くようになったらスタート可。

## 14. 実装上の注意（順序と規律）

- **先に各機能を簡易実装して全ての処理順・動き・ロジックを実装**（統合は後だと難しいため、先に処理フローに
  エラーや明らかな遅延がないか確認）。
- 各機能の具体的なコード/技術は**実装直前にプランニング**。各機能は**ブランチを切って試行錯誤**、完成後マージ、必ずテスト。
- タイムスタンプで**過去のことを話していないか**を見る。リアルタイム性を重視。発話の自然さは Opus 4.8 で出す。
  先に応答予想をして、どれくらい違ったか・自然な応答かを分析。
- テストは2度以上・**2連続成功で合格**。**マージ前の最終テストは5回以上成功**。
- 信頼度を考慮した情報収集（論文・一次情報・SNS・コミュニティ等を幅広く）→ 確認・議論・レビュー・実装・テストを
  **3エージェント以上で議論**しながら。意見が割れたら多数決→多い方を再調査、**全会一致で実装**。
  少しでも曖昧な点があれば必ず報告・質問。
- まず1ファイルごとにサルベージ（SALVAGE_MANIFEST）→ 新企画書に従い**統合パイプラインから作成**→
  その後**各機能の実装優先順位**を考える→各機能のプランニング→実装。
- 過去参照していないか・パイプラインに破綻がないかも要テスト。**ペルソナは一旦外して挙動を見る**。

## 15. 現状の問題（モチベーション・v1）

- 音声認識の聞き間違いが激しい。RAGの構造が弱く、過去の記憶から話が展開されない／今の会話と絡まない。
- 画面認識が YOLO 等の低レイヤーでハルシネーション多く遅い。全体的に応答が少し遅い。
- 1年半かけて作ったため古い部分は技術が古い。システムプロンプトが多くシステムに影響（ペルソナは一旦外す）。
- フィードバックは特に FEP 部分を大幅に変える。UIが画面外に隠れてスタートが押せず不便→完全に変えたい。
- 自律的発話がほぼ無言か直近会話由来で不自然。タスクが完了しない/無視/文脈破綻しても疑問に思わず解答のみ返す。
- 変に既存コードがあるための非合理な引用・似たコードは嫌。**本当に合理的・客観的・最適な時のみ**既存ロジックを使う。
